# Notification/lifecycle integration — research and judgment

16 October 2026. This extends the existing service comparison and native UI plan, not a new design audit.

- [Android notification permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission): ask from a relevant deliberate action using RequestPermission. Denial/swiping is not authorization; settings may block the app or channel independently. Adaptation: the existing Owner-attention settings card has a notification action. Startup, resume, policy saving and notification taps never prompt. After an attempted request, another deliberate action opens Android settings rather than repeatedly asking. The in-app worklist remains available.
- [Android notification navigation](https://developer.android.com/develop/ui/views/notifications/navigation): preserve the normal app navigation experience. Adaptation: immutable generic PendingIntent enters the existing native activity, which retains a navigation request across ordinary authentication/recreation. Current supported role and existing destination readers still enforce authority; a marker is not a sign-in. Existing host leave guards run before navigation, and the existing Customers screen opens its Follow-ups pane. Back returns through Customers and More. No composer opens.
- [Android persistent-work requests](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work): constrained periodic work runs inexactly and may be deferred. Adaptation: reuse six-hour network-constrained unique work and coalesced one-time checks; no exact preferred-minute promise. The fresh detector's server policy, primary identity, quiet hours, day reservation and durable grant rules remain unchanged.

Inspected actual Application startup, Activity foreground/authentication, three role-host draft guards, Owner More refresh/customer controllers, SyncScheduler command choke point, public drain/pull wrappers, token/binding clearing, and the detector/store/worker. The simpler alternative—posting directly after a local edit or trusting a notification marker—would bypass fresh shared checks. Instead, hooks mark derived attention stale and request the existing detector. No fake local Owner login is created. A local app lock/logout does not equal server disconnect; the selected authenticated primary device may continue its existing protected background work. Server disconnect, unsupported identity/contract or disabled policy stops periodic work and cancels the generic notification. Unknown/offline failures retain stale attention and retry without treating cached state as fresh.

Worker-owned drain/pull disables recursive follow-up kicks; ordinary drain/pull and committed command hooks request checks. Invalidation serializes with detection under the same gate, so a previously scheduled detector cannot overwrite a later invalidation without a subsequent check. Count files contain no customer details and remain outside portable backup. Reopening persisted state is stale. Existing KEEP semantics coalesce a kick already queued/running; periodic work and later foreground/sync events provide eventual refresh, not an immediate-count or elapsed-scheduling guarantee.

The independent judgment hook was applied before coding and at finish. It is a reminder, not an independent reviewer, server approval or proof that Android delivered a notification. Focused fixtures and platform permission checks can verify the local paths; actual DEV/two-phone integration and ordinary signed delivery remain retained acceptance work. No SMS provider or automatic customer sending is activated.
