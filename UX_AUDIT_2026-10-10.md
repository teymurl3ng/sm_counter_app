# Motion, feedback, readability, catalog, and daily access audit

Date: 10 October 2026. Status: **source audit and external research completed; physical reproduction and visual acceptance pending**. Application implementation has not been changed by this task.

## Evidence boundary

The launcher alias `.Main` targets `nativeui.NativePreviewActivity` in the current manifest. This audit therefore focuses on the shipped Compose presentation, its native facades, permissions, catalog, and date locks. The retained hybrid interface is a compatibility dependency for later changes, not evidence that the active UI reloads a web page.

The source sweep inventories **130 native UI Kotlin files, 71 screen/host/shell files, 65 transition call sites, 24 ViewModels, and 992 existing control-inventory rows**. See [the evidence folder](audit/2026-10-10/ux/README.md). Each screen file has an explicit runtime status. Shared components, hosts, and high-risk implementations were inspected directly. Search counts are not a claim that every branch or every control received a physical test.

The working tree already contained substantial application edits. Findings refer to that working tree, with native UI hashes recorded. Earlier phase documents and COVERED test labels were treated as context, not acceptance evidence.

The designated A06 is connected. Read-only package inspection found ordinary version 5 / 0.4.1 and isolated QA version 4 / 0.4.0-qa. The ordinary package version agrees with the current build configuration, but neither version number proves the binary matches the dirty source. No package was installed, launched, cleared, or interacted with. No screen recordings were taken. **This is not an all-screen device PASS.** A matching isolated build and repeated-route recordings are the first scope gate.

Classification: **confirmed** means demonstrated by implementation or calculation; **risk** means a plausible failure mechanism requiring reproduction; **reported** means the user's observed behavior has not been independently reproduced; **proposal** is a recommended adaptation, not an industry requirement.

### 1. Authentication and recovery

`NativeAuthenticationScreens.kt:91` animates the entire auth frame using state class as its content key. Picker → method → PIN/passphrase → recovery replaces the whole header and body through the shared fade/scale helper. `NativePreviewActivity.kt:934,965` adds outer welcome/access and auth/role-shell transitions. Busy/error changes within the same class are grouped, so it is inaccurate to say every auth update triggers a transition.

`NativeAuthenticationViewModel.kt:95` selects the account by assigning MethodPicker or Passphrase. It does not load a URL, recreate an Activity, or reload a WebView. Startup and account switching do use a Loading state. The observed impression of reloading has a credible native explanation; a literal full-page reload is not supported by this path.

`RecoveryCodeScreen` uses the same `AccessFrame` as other auth steps. `AccessFrame` applies `safeDrawingPadding()` before painting its green header (`NativeAuthenticationScreens.kt:650`). In contrast, `CashierScreenHeader.kt:52` paints the green surface first and pads its contents inside the status-bar area. This confirms a visual construction mismatch. The recovery step also removes the Back row, changing header height. Existing safe padding falsifies the simple claim that this screen has no top-inset handling.

**Risk:** the whole-frame scale/size transition, changing header height, and keyboard/inset timing could produce intermediate clipping. Verify settled and transition frames after creating an owner with the keyboard visible, portrait/landscape, large text, and animations disabled. Do not add arbitrary padding without locating the failing frame. Never capture a real recovery code as audit evidence.

**Proposed adaptation:** one stable auth scaffold and inset owner; animate the step body, preserve relevant focus and account context, and retain a static accessible recovery page until explicit acknowledgement. Android documents how inset padding is consumed and why it must be applied at the correct container. [Android window insets](https://developer.android.com/develop/ui/compose/system/insets-ui).

### 2. Navigation, warm refresh, and flashing

`NativeAsyncUi.kt:169` fades incoming content from zero and scales 0.92 → 1 over 200 ms, while outgoing content exits in 1 ms. This can expose the container while the next pane is still transparent. Its comment calls the transition fade-through, but its spec does not sequence the normal outgoing and incoming phases. The comment also promises no size morphing, without explicitly disabling AnimatedContent's size transform. Whether size changes in a particular full-size container needs measurement.

Owner, Manager, Admin, and Operations hosts have a section transition around another destination `AnimatedContent`. Their destination spec scales 0.96 → 1 with `ExitTransition.None`. Saying the new content is opaque does not make its shrinking bounds cover the entire previous pane. Entry wrappers can additionally animate Idle/Loading → Ready on the first open; other screens add pane transitions. This explains why first entry and warm entry can take different animation paths, but is not a filmed root cause for the user's symptom.

**Confirmed refresh race:** Owner, Manager, Admin, and Operations Work ViewModels capture `previousDestination`, suspend for their context load, then construct Ready using that captured destination. `openDestination()` and `backToHome()` do not invalidate that load. Reproduction by event ordering:

1. Refresh starts at Home and captures Home.
2. User opens ReceiveMilk or Deliveries while Ready content remains interactive.
3. Load completes; its current request is still valid.
4. Ready is rebuilt with Home, overwriting the user's newer destination.

The failure branch can restore the older state too. Relevant implementations: `NativeOwnerWorkViewModel.kt:91`, `NativeManagerWorkViewModel.kt:88`, `NativeAdminWorkViewModel.kt:81`, `NativeOperationsWorkViewModel.kt` refresh. This is a navigation correctness defect independent of motion taste. It can trigger extra pane switches; attributing every flash to it would exceed the evidence.

Records pane transitions also read live outer detail/correction state while animating an older pane (`OwnerRecordsScreen.kt:130`). Clearing that state can make an outgoing branch return early. A transition must render the state associated with its content, as Android's AnimatedContent example explicitly demonstrates. [Android animation guidance](https://developer.android.com/develop/ui/compose/animation/composables-modifiers).

**Proposed adaptation:** one owner for each navigation transition, stable opaque screen containers, route identity independent of loading/data state, current-destination merging on refresh completion, preserved drafts/scroll, and nonblocking warm refresh. Use interrupted-navigation recordings to decide transition geometry; do not fix flashing by adding delays.

### 3. Haptics

The sweep finds direct haptic calls in 21 of the 71 screen/host/shell files. Fifty have none, but many are wrappers, so that number is not fifty broken screens.

Individually confirmed omissions include auth account/method/primary buttons, ProductSelector's ProductCard selection, and Products/Employees list rows. The shared press-scale helper is visual feedback, not a vibration implementation. Other sale controls, role navigation, and commit buttons explicitly call haptic helpers, producing an inconsistent vocabulary.

`Haptics.kt:22` uses the Vibrator service directly. It does not check an app haptic preference, Android touch-feedback preference, or explicitly select a no-vibration fallback for poor hardware. Commit and destructive helpers use the same predefined heavy-click effect on Android 10+, and tap and success use the same click; the different fallback durations do not distinguish them on that path. Receipt `LaunchedEffect` calls can replay on screen remount because remembered event state is not globally consumed.

The file's statement that all View haptics fail on an A06 is a historical assertion, not verified here. Do not remove its fallback solely because normal Android guidance prefers semantic effects.

Android calls for consistent feedback for similar interactions, restraint for frequent events, semantic predefined effects, and suppressing custom touch vibration when the user disables touch feedback. Haptics supplement visual feedback. [Haptic principles](https://developer.android.com/develop/ui/views/haptics/haptics-principles), [haptic APIs and preferences](https://developer.android.com/develop/ui/views/haptics/haptics-apis).

**Proposed adaptation:** a shared semantic dispatcher for selection, accepted action, actual success, rejected action, and destructive confirmation; control-by-control expected-feedback inventory; user/system preference support; once-per-outcome success delivery. Success vibration must follow a verified write, not the initial Save tap.

### 4. Catalog and sale breadth

`NativeSaleFacade.kt:93–116` creates rates only for Milk/Yogurt, then drops products with no matching exact/prefix name. Consequently Cheese disappears; a name starting with Milk inherits the Milk rate regardless of its own catalog price. Prefix matching was added for renamed probe items but makes a product's name determine financial defaults.

The catalog already stores `ProductProfileEntity.defaultSaleRate`, exposed by `ProductCatalog` and `NativeOwnerProductsFacade`. `ProductReferenceDto` does not carry it, and the sale facade does not use it. This is a gap between catalog and sale capability, not merely two hardcoded UI buttons.

`CashierSaleScreen.kt:935` iterates every supplied product. Its unstacked layout assigns each card an equal share of one Row: additional products become narrower. Deliveries independently lists all unarchived catalog products, so products can appear there while absent from Sale.

Broader limits remain: `ProductCatalog.kt:93` accepts only Liters/Kg; production is Milk-to-Yogurt; some costing/opening-basis and dashboard logic matches Milk/Yogurt. A configurable shop name plus an unfiltered picker does not validate a general retail app.

Square offers catalog-backed quick tiles and categories; Shopify supports product search/browse/add-to-cart. These are familiar scaling patterns, not proof we need barcode scanning, all their features, or a multi-line cart in this repair. [Square item grid](https://squareup.com/help/us/en/article/8334-set-up-item-grid), [Shopify POS product search](https://help.shopify.com/en/manual/sell-in-person/shopify-pos/inventory-management/searching-for-products).

**Proposed adaptation:** product-ID-based price and availability, quick access for a small catalog, searchable/wrapping access as it grows, explicit behavior for missing prices and archived stock. Decide supported product/unit/costing breadth before calling the result general-purpose. Existing `PRODUCT_SCOPE.md` explicitly requires this boundary.

### 5. Business identity

Confirmed literals exist in Welcome (`native_app_name`), account-selection titles, auth and recovery copy, and Android resources `app_name`, `login_title`, `native_app_name`, and `native_brand_mark`. Other native screens already use `context.shopName`; the Owner shell often shows the signed-in person's name. Identity is inconsistent, not universally hardcoded.

Distinguish merchant identity, signed-in user identity, and installed product identity. Show the configurable shop name in business-facing UI and outputs; keep actor identity separately. Use neutral auth text where a trusted local shop name is unavailable. Resource/class/package names, backup identifiers, sync UID namespaces, and cryptographic domains must not be renamed as a text-replacement exercise.

Shopify treats store name as configurable store details, separately from organization/internal identifiers and its domain. This supports the separation, not an instruction to copy Shopify branding. [Shopify store details](https://help.shopify.com/en/manual/your-account/manage-orgs-and-stores/manage-store-details).

**Proposed adaptation:** a shared observable business-identity read model, immediate refresh after settings save, truthful neutral first-run fallback, long/Urdu-name tests, receipt/export/notification review, and an explicit separate decision about the Android launcher product name.

### 6. Lists and readability

Products (`OwnerProductsScreen.kt:782`), Employees (`OwnerEmployeesScreen.kt:701`), and Records (`OwnerRecordsScreen.kt:950`) draw clickable Rows without a distinct row surface. The containing scaffold uses the page background; list separation relies on outlineVariant dividers. Product/Employee primary names are already semibold 16sp, so saying all text has the same hierarchy would be wrong. The secondary 14sp muted text is still weak on this background.

Reproducible token calculations from `SaafTheme.kt`:

| Pair | Contrast | Interpretation |
|---|---:|---|
| Ink / light page | 14.77:1 | Strong primary text |
| Muted / light page | 4.414:1 | Below normal-text 4.5:1 benchmark |
| Muted / light surface | 4.901:1 | Meets that benchmark at full opacity |
| Muted / light surfaceVariant | 4.035:1 | Below normal-text benchmark |
| Light surface / light page | 1.110:1 | Weak surface separation; not itself a text failure |
| outlineVariant / light page | 1.154:1 | Very faint separator |
| Dark surface / dark page | 1.103:1 | Separation also needs dark-theme review |

Do not round 4.414 up to a passing value. Opacity, disabled states, mixed backgrounds, and text size must be assessed at the actual use site. WCAG requires 4.5:1 for normal text and 3:1 for sufficiently large text; those thresholds are useful accessibility acceptance benchmarks here, not a claim of a full native-app compliance audit. Decorative dividers do not universally need 3:1. [W3C contrast explanation](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

**Proposed adaptation:** a shared list system: distinct grouped surfaces where appropriate, sufficient text contrast, strong name/amount hierarchy, quieter metadata, visible selected/pressed/disabled states, stable amount alignment, and readable multi-line names. Avoid turning every dense record into a large card; choose by task and density. Compare Products, Employees, and Records before rolling the component across every inventoried list.

### 7. Outcomes, progress, failure, and confirmations

`OwnerProductsController.kt:193` creates a product, reloads the list, and closes the form with no explicit success outcome. Product create/edit/detail and many other master-data flows switch through immediate Boolean/detail branches rather than a dedicated semantic pane transition.

Nine ViewModels auto-clear receipt state after four seconds: Collection, Drawing, Expense, SalaryPayment, VendorPayment, ReceiveMilk, MakeYogurt, RecordSpoilage, and CashClose. Sale currently retains its receipt until explicit action. A transaction receipt is a different information need from a transient notification; automatic clearing can remove reference numbers before the user is finished reading.

`CashCloseEntryScreen.kt:180` directly swaps form and receipt within Ready. A transition keyed only on Ready's class does not animate that change. Deliveries inserts success content inline. Therefore a global animation helper does not by itself give consistent result transitions.

The app is not entirely silent: Sale/Collection have detailed receipts and some flows expose live-region errors/results. Snackbar infrastructure exists; native showSnackbar usages found by this sweep are primarily fixture/bootstrap messages. The inconsistency is the confirmed issue.

Android identifies saved-form confirmation as an appropriate snackbar use, while W3C status-message guidance stresses accessible announcements without forcing focus. [Android snackbars](https://developer.android.com/develop/ui/compose/components/snackbar), [accessible status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).

**Proposed adaptation:** semantic Idle → Working → Succeeded/Failed outcomes shared across writes. Use a brief accessible notification for routine settings/catalog saves, persistent receipt for money and important operations, inline actionable failure with preserved inputs, and a confirmation dialog only where consequence merits interruption. Animate both entry and dismissal as UI transitions; never delay the underlying write or invent processing time. Saved locally, sync pending, and synced are separate facts.

### 8. Starting and closing the day

Current facts:

- `DailyCloseDao.isPostingClosed()` locks a date when an active close at that date or a later date covers it, except for an explicit active reopen at that exact date. Thus a new date later than the latest closed date normally accepts posting automatically. There is no closed-until-open state or OpenDay permission/event.
- `RolePermissions` grants Cashier `CASH_COUNT_AND_CLOSE`; `NativeCashCloseFacade` and authenticated `DailyCloseService` enforce it. Native actor-role validation allows Cashier to close. CashierMore offers only blind count; the global day chip is passive for Cashier. The host comment that Cashier cannot close is contradicted by the policy.
- Native Admin also retains broad close/reopen authority while its current shell does not expose the same day-chip flow. Permission labels, UI, and domain authorization need one reconciled matrix.
- Reopening requires separate `REOPEN_DAY`, recent full authentication, and a reason. Current domain roles are Owner/Admin; Manager/Cashier cannot reopen.
- Today's close can cover earlier unclosed dates. This is more consequential than ending a single cashier's shift.

Actual product patterns differ. Lightspeed R-Series explicitly allows sales associates to close registers and offers separate Open Register and Close Register permissions. Shopify has a staff permission for starting/ending payment-tracking sessions, allows automatic opening on the next sale, and describes starting float/final count; its closed register sessions cannot be reopened/edited. Square distinguishes ending a drawer from closing it with an actual count. [Lightspeed staff permissions](https://retail-support.lightspeedhq.com/hc/en-us/articles/229129608-Setting-up-employee-roles-and-access), [Shopify POS permissions](https://help.shopify.com/en/manual/your-account/users/roles/permissions/pos-permissions), [Shopify register sessions](https://help.shopify.com/en/manual/sell-in-person/shopify-pos/cash-register-management/register-sessions-in-shopify-pos), [Square drawer sessions](https://squareup.com/help/us/en/article/8344-start-and-end-a-cash-drawer-session).

**Recommendation:** a clerk entrusted to operate the counter should be able to start routine work and submit a closing count without an owner standing beside them. Do not grant broad admin access to solve that need. For the present single-shop daily model, expose the existing Cashier close flow only after explicitly confirming its whole-day locking scope, show dates/pending deliveries/variance before closing, preserve actor attribution, and keep reopen separate. If different shifts/devices need independent closure, implement register sessions as a separate capability rather than redefining the daily close silently.

There is no universal industry rule that every cashier may close the entire business period. Delegated permission and clear accountability are the transferable patterns. A configurable close permission or count/close split is a policy extension, not a theme-only fix.

## Research conclusions and scope handoff

External documentation provides requirements or established patterns; it does not prove competitor apps never flash or that their designs fit this business. Official help documentation was used to verify actual workflows, with Android/W3C used for implementation/accessibility criteria. JavaScript-only Material pages supplied little readable evidence and were not used to assert exact timings or a mandatory visual style.

The smallest useful adaptation is a stable native shell, consistent readable list components, semantic outcome feedback, selective consistent haptics, catalog-backed sale choices, and a reconciled day-access policy. Generic inventory/costing expansion and register sessions are separate capability decisions.

See [the scope proposal](UX_SCOPE_PROPOSAL_2026-10-10.md) for implementation boundaries, dependencies, decisions, and the complete physical acceptance protocol. **Do not mark the reported flashing or recovery clipping closed from this source audit or from a successful build.**
