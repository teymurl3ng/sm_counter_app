# Identity backup operations

`identity-dr` saves the PROD identity tables and Auth-user metadata to this private repository's `identity-backups` branch on Mondays at 06:00 UTC (11:00 PKT), or by manual dispatch. It is a sequential export, not an atomic database snapshot or a full shop ledger backup. Exact disaster recovery needs a maintenance boundary or a separately verified consistent backup. Raw Auth metadata contains private identity information; retain this repository's private visibility and restrict access. API keys are read from existing GitHub Secrets and are never written by the collector.

Each successful run adds a unique UTC timestamp directory with seven payload files and a `manifest.json` containing target project, start/finish times, row counts, SHA-256 hashes and workflow/source provenance. The collector paginates until exhaustion, rejects duplicate rows, validates counts/hashes before success and refuses a URL outside the expected PROD project. Legacy service-role JWTs and modern server secret keys are supported. Snapshot work begins after checking out the backup branch; only the new directory is staged, and workflow concurrency serializes branch writes. Existing snapshots are retained. Failed collection must not publish a partial directory.

To check freshness, open [identity-dr runs](https://github.com/teymurl3ng/saaf-milk-account-server/actions/workflows/identity-dr.yml), inspect the newest successful run, then check the corresponding manifest on [identity-backups](https://github.com/teymurl3ng/saaf-milk-account-server/tree/identity-backups). A job failure means no new accepted recovery point; an older green run does not make the current backup fresh. Manual runs are bounded acceptance checks, not a replacement for the weekly schedule. GitHub schedules can be delayed; verify the saved timestamps instead of assuming the cron ran precisely.

For failure alerts, enable GitHub Actions email/web notifications and choose “Only notify for failed workflows” if preferred. Scheduled-run notifications depend on who last changed the cron syntax; verify recipient settings. These settings are not changed by this workflow. See [notification settings](https://docs.github.com/en/subscriptions-and-notifications/how-tos/managing-github-actions-notifications) and [scheduled-run notifications](https://docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs). GitHub's 60-day inactivity auto-disable rule applies to public repositories; this repository is private. See [schedule behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

The seven files are raw snapshots, not the combined portable export consumed by `recover_identity.py`. Do not run the current in-place emergency wiper against PROD or shared DEV. Stable-ID/actor-preserving conversion and empty-destination restore acceptance are separate work. New credentials must be issued for eligible accounts during verified recovery; old passwords are not recovered from these files. App portable backup secrets, server credentials and the APK signing key are distinct custody needs. The snapshot does not include app ledger/Drive objects, signing keys or the private reset reservation schema. Pending-reset recovery remains a separate explicit boundary.

When main source is repaired, retain the old snapshot folders as historical points. Do not force-push, delete them, rewrite remote migration history or weaken reset/last-Owner guards to make recovery appear successful.
