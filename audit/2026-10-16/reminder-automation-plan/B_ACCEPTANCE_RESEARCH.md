# Live acceptance research and independent judgment

16 October 2026. Inspected the deployed DEV RPC fingerprints, committed v1 SQL, original DataStore/codec, native workspace adapter, shared handoff adapter, accepted physical Credit fixture, native Activity/authentication and existing three role hosts. No server implementation or product feature is added by this acceptance harness.

Reviewed the current [Supabase changelog](https://supabase.com/changelog), including the [upcoming CBC cipher removal](https://supabase.com/changelog/cbc-tls-ciphers-deprecated), and [database function authorization guidance](https://supabase.com/docs/guides/database/functions). Existing Android HTTPS is used without weakening TLS. Each phone signs in through the real DEV Auth/enrollment and current leadership RPC checks; private tables are not exposed to the mobile test. Admin access is used only by the existing host fixture helper to create/retire the exact synthetic shop/staff and inspect unrelated public-row hashes. No service key reaches Android.

The earlier contract checks did not prove overlap, so this story does not inherit that conclusion. Both devices prepare against the same current heads and wait for a timed barrier, then issue distinct durable ACQUIRE requests. Device clocks are bracket-sampled from the host; overlap is evaluated after shrinking the measured intervals by calibration uncertainty. One accepted reservation plus one shared live preparation is the expected result. A sequential or inconclusive run must remain so labeled. This verifies well-behaved clients and shared coordination, not hardware identity attestation or freedom from all races.

Deliberately losing an already accepted START reply checks the dangerous boundary: the fresh process must recover the original request and receive no launch grant, while the other device must remain blocked until explicit review. A successful handoff uses a counted callback, never a real recipient app. It proves authorization/callback accounting, not sending or delivery. Primary transfer plus original/daily DIGEST replay checks reservation identity; it does not wait six hours or claim exact-time Android delivery. Earlier platform notification tests cover actual private generic notification posting and permission/channel behavior separately.

Native cold/recreated/warm entry is exercised through the real QA Activity and a synthetic local owner signing in through the ordinary account/passphrase screen. The destination readers retain their authority checks. This route check is separate from hosted authorization and does not pretend that a notification marker authenticates an account. Existing dirty-draft guards were already verified in the scoped integration checkpoint; no new broad form audit belongs here.

The hook is a judgment reminder, not an independent approval. Passing fixtures cannot establish a real shop's staff readiness, private acceptance or independent key custody. Production migration and ordinary signed rollout remain explicit later steps. Unexpected unrelated findings are retained for later rather than expanded into this run.
