## Implemented and verified

Two authenticated RPCs expose private shared settings/customer preferences, review/snooze state, per-customer preparation/handoff claims and one notification reservation per shop day. Only current active server leadership with shop access may use them; Owner alone changes shop policy/primary assignment. The six private tables have RLS and no anonymous/authenticated direct access. No balance, financial record or customer phone/name copy is stored by this contract.

Each operation uses the existing sync shop lock and accepted financial/Credit/follow-up heads. Schedule versions are separate from edit versions: quiet hours, pause and primary changes do not recreate statement cycles. Five-minute preparation leases may expire; a started handoff cannot. An original accepted start can grant one launch; a recovered/replayed start cannot grant another. Unknown handoffs require an explicit, exact-attempt operator resolution, not a timer. Notification reservation retries similarly cannot authorize another alert.

DEV migrations are `20261016110904_customer_followups_v1` and `20261016112511_followup_actor_indexes`. Files were created with the CLI and aligned to the actual verified remote versions. The second migration covers only the new actor FKs flagged by the performance advisor; it makes no behavior change. No existing shop was opted in.

**72 rolled-back SQL checks pass**: [results and earlier fixture corrections](B_CONTRACT_CHECKS.json). They cover server roles/isolation, explicit activation, malformed policy/schedules, CAS edits, schedule version stability, pause/snooze, stale heads, lease ownership/expiry, idempotent and uncertain handoffs, explicit resolution, primary transfer, one daily reservation and absence of financial writes. No whole-app suite or new Android build was needed for these SQL-only changes. Quiet-hour worker behavior and actual notification display still need the planned Android checks; these SQL results do not substitute for them.

## Independent judgment and current research

The saved hook is a reminder, not external approval. Inspected the actual existing sync lock, actual server membership/roles and new RPC paths. A local checklist would be simpler for a permanently single-phone shop, but cannot supply the accepted shared retry/recovery semantics. A short lease alone is inadequate after a composer may have opened; retaining uncertainty is the safer supported behavior. Current database checks support the contract at the documented scope. They do not establish physical concurrency, fresh knowledge of offline collections, exactly-once delivery, notification display or device attestation. Installation strings coordinate well-behaved clients; they are not the separate deferred staff/device identity system.

Current primary sources: [Supabase functions](https://supabase.com/docs/guides/database/functions), [API grants](https://supabase.com/docs/guides/api/securing-your-api), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) and [Postgres advisory locks](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS).
