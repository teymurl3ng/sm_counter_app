## Executive summary

The app is **not spaghetti**. The architecture is deliberate and navigable (uniform facade/state/viewmodel triads, clean layering, a real design-token system with zero hardcoded colors, an instrumented contract-test wall, and unusually honest product writing). The frozen-spec discipline is real and mostly holding. Where this project is exposed is specific and fixable:

1. **The sync engine has no conflict policy at all** — and its normal reconnect path silently destroys unpushed local edits. (Critical)
2. **The verification infrastructure is one Windows machine and two phones** — no CI, and the money/close/corrections/sync core has zero JVM tests, so the codebase's best-hidden bugs are exactly the ones no machine checks. Two of the project's own gates currently FAIL on the tip. (Critical)
3. **Two frozen-spec clauses are implemented on the wrong side**: offline-grace blocks *reads and sign-in* (spec: writes blocked, reads allowed), and token refresh *wipes the session* on transient network Unknown (spec: UNKNOWN never revokes). (High)
4. **Three workflow sharp edges around the daily close** that a real milk shop will hit in its first skipped-close week. (High)
5. **A cluster of one-paisa/tolerance inconsistencies** in money math that will surface as "the numbers don't add up" disputes. (Medium)

**Counts (after triage):** 2 Critical · 12 High · 27 Medium · 20 Low/Info · ~15 owner decisions · 24+ deliberate-design confirmations. Detailed evidence for every item below.

## CRITICAL

### C1. Sync has no conflict detection or last-writer-wins; the pull-before-push reconnect path silently erases unpushed local edits — verified
`data/SyncEntities.kt:78-121` — every `SyncApplyDao` UPDATE is `WHERE uid = :uid` with no `sync_updated_at` comparison; the stamp is written, never read as a guard. `sync/SyncApplyEngine.kt:119-155, 307-424` applies pulled rows unconditionally; `sync/SyncEnvelopeFactory.kt:73-110` pushes full-row snapshots; `sync/SyncRuntime.kt:64-112` orders pull-before-push.
Two devices edit the same product/account/settings row offline. On reconnect, device A pulls B's row, its local edit is overwritten, and its outbox then pushes the already-overwritten row. The local edit exists nowhere, on any device, ever. This is the *normal* offline-reconnect path, not an edge case.
**DOC CHECK: FAILED** — no md documents any conflict policy; the "LWW" attribution in earlier recon is wrong (the stamp is not a guard). The push-side halt-at-head is documented and correct; the pull side has nothing.
**Why it bites:** a ledger where a price/category correction made on one phone can silently vanish is a data-integrity defect at the product's core promise.
**Owner decision:** is "server order wins, silent overwrite" acceptable? If not: guard on `sync_updated_at` + conflict audit rows (the apply engine already has the audit vocabulary), or field-level merge for master-data tables.

### C2. The entire quality gate is one Windows workstation + two phones; core money logic has zero JVM tests — verified
No CI config exists anywhere (no `.github/`, no other CI system). `phase18/build.gradle.kts:167-171` hard-blocks instrumented tests without `-Psaaf.instrumentationSandbox`; README records the 273/273 device regression as *the* release gate. `app/src/test/` contains 6 files / 355 lines total; `domain/Costing.kt` (780 LOC), `DailyClose`, `Correction`, `Sale`, and the whole 23-file `sync/` package are covered only by device tests.
The deliberate device-first posture is documented (POSTMORTEM §9; see Appendix A) — but its consequence is that **every safety net requires a human, a cable, and a Samsung**. Corroborating evidence from this very audit: the two host gates that *do* run automatically are the two that failed (`qaFast` inventory drift, lint errors) — see M1/M2.
**Why it bites:** machine loss, skipped regression between merges, and un-refactorable domain code (no fast test loop → copy-paste pressure). The duplication cleanups in the fix menu are directly cushioned by these tests; they're also unreachable without a device.
**Owner decision:** self-hosted runner attached to one shop phone is the cheapest real fix; a JVM test base for domain math is the second.

## HIGH

### H1. `refreshSession()` wipes the stored session on ANY non-Allowed result — including transient network Unknown — verified
`sync/SyncRuntime.kt:133-152` (`else -> { tokenStore.clear(); setSchedulingEnabled(false) }`); `sync/AccountAuthClient.kt:138-141` maps any refresh 400 without `invalid_credentials` to `Unknown` — and Supabase actually sends `invalid_grant`/`refresh_token_not_found`, so even a legitimately dead token lands in the session-destroying bucket. **DOC CHECK: FAILED vs frozen spec** — `ACCOUNT_BRIDGE_PHASE1_SPEC.md` §5: "UNKNOWN … never revoke." One timeout mid-drain silently de-syncs the device until manual re-enrollment. Also compounds H2.

### H2. No mutex anywhere in sync/ — concurrent drains race, and the losing refresher deletes the winner's fresh tokens — verified
Zero `Mutex|synchronized` in `sync/`; `MilkShopApplication.kt:44-54` launches start-up pull + push kick concurrently; owner "Sync now" (`OwnerSyncController.kt:142-175`) runs parallel to any kicked worker; a second SyncRuntime instance exists (`NativeOwnerSyncFacade.kt:23`). Two 401s → two refresh POSTs → under rotation, the loser's non-Allowed result clears the winner's session (via H1). Duplicate pushes also occur — **survivable**: I verified live on both Supabase projects that `sync_push` upserts idempotently by `(shop_id, table_name, row_uid)`.

### H3. Apply-engine per-record catch inside the shared transaction can commit a half-applied event that re-apply can never repair — verified
`sync/SyncApplyEngine.kt:52-109` — one write transaction per batch, per-record try/catch with no savepoint; `applyEvent` inserts the event header at `:208` *then* parses children (`:210-241`) — a child parse failure commits header-without-ledger-rows; the uid-skip at `:160` makes re-apply a permanent SKIPPED. Ledger totals silently diverge between devices.

### H4. The trusted-time BusinessDateGuard is wired ONLY on the dormant hybrid path — the shipped native product has no date bound at all — verified
All 11 guard call sites are under `application/bridge/` (grep-verified); native facades use `BusinessClock.today()` defaults with no guard (e.g. `NativeDeliveriesFacade.kt:29` + 15 siblings). A device with a wrong clock can post events for any date, and the corruption syncs everywhere. `BusinessDateGuard.kt:7-15` documents the policy without binding it to a path.

### H5. Offline-grace expiry blocks reads AND sign-in — the frozen "writes blocked, reads allowed" policy is implemented on the wrong side — verified
`domain/Security.kt:453-468` gates *every* permission on grace expiry; `NativeAuthenticationFacade.kt:203` runs `identity()` → `requirePermission(VIEW_OPERATIONAL)` right after login. An owner offline >7 days cannot open the app at all (login succeeds, then PermissionDenied; quick unlock fails identically). The code comment at `:459-461` claims reads stay available — the implementation does not do that. **DOC CHECK: FAILED vs frozen spec §6.** (Note: the grace logic lives in the local auth layer; `sync/` correctly has none.)

### H6. Room database is plaintext at rest; all local security is app-level gating — verified (threat-model decision needed)
`data/MilkShopDatabase.kt:223-231` (no SQLCipher/SupportFactory; no dependency in the catalog). Mitigations are real (allowBackup=false, full backup exclusion, FBE, app-private dirs), but anything running as the app UID (root, Frida, malicious same-UID on the *shared shop phone* that QUICK_UNLOCK_REQUIREMENT itself names as the threat model) reads every financial record, verifier, and audit row. **No document records this as an accepted risk.** Owner decision: accept-and-write-down, or add SQLCipher.

### H7. The native sale flow cannot apply the Delivery Surcharge the spec requires — verified
`domain/Sale.kt:76-84` implements it; `application/sale/NativeSaleFacade.kt:41-54` has no surcharge fields; `CashierSaleScreen.kt` has zero surcharge UI. Only the dormant hybrid path (`OperationsBridgeHandler.kt:153-172`) and sale *corrections* can set it. Spec §7: "Delivery Surcharge (optional toggle, defaults ₨50…)" — §13.1 resolves it applies to any sale. At hybrid cutover the capability silently disappears from the product.

### H8. Closing today silently seals every earlier never-closed day, which can never be reopened in their own right — verified; owner decision flagged
`data/Phase3DailyCloseDao.kt:10-34` (`isPostingClosed` matches any unlocked close with `business_date >= :date`); `domain/DailyClose.kt:123-124` (reopen errors "has not been closed" for a day with no close action); the close UI operates on today only (`NativeCashCloseFacade.kt:88-91`). Skip Monday's close, close Tuesday → Monday is frozen un-postable forever, with no per-day seal record. The DB-level behavior is internally coherent (data pass confirmed app/DB agree), but **no document sanctions absorbing un-closed days**, and no UI explains it.

### H9. A day can be closed with pending deliveries, which then freeze — no warning, no block — verified
`domain/DailyClose.kt:65-101` (close gate = latest Cash count + variance reason only); `NativeDeliveriesFacade.kt:212-224` blocks marking a closed-date delivery delivered. Real flow: milk delivered on day D, manager closes D → the row sits unconfirmable; recovery runs through H8's reopen. The workflow doc lists "close blockers" as a concept but doesn't include deliveries, and the close dock's "repeats the consequence before a write" rule is not honored here.

### H10. Baseline enqueue order applies daily_close_actions before physical_cash_counts; receiving devices permanently lose close↔count links — verified
`sync/SyncBaseline.kt:27-29` and `data/SyncMigrationSql.kt:255-266` enqueue in the inverted order; `SyncApplyEngine.kt:393-395` nulls `count_uid` when the count isn't applied yet (no skip), and `:392` never repairs already-applied rows. Cash-reconciliation history diverges silently on every fresh receiving device.

### H11. Dark-mode contrast failures on the Owner's money-attention banners — verified (static)
`owner/OwnerOverviewScreen.kt:168-170` — `SaafYellow.copy(alpha=0.35f)` + `SaafInk` over the dark background composites to ≈2.2:1; `OwnerReportsScreen.kt:287-296` complete-banner ≈1.4:1 (near-invisible). WCAG AA needs 4.5:1; both pass in light mode (13.2:1 / 5.3:1) so this ships silently. Raw tokens don't flip for dark by design (Appendix A) — these two call sites are the documented-gap exceptions.

### H12. `demo-crossfade` is an active, non-ancestor parallel line; merge-to-main is 98 commits deep — verified (git)
`git rev-list/cherry`: all seven `codex/*` + `fix/*` branches are fully merged (stale litter, safe to delete); **demo-crossfade holds 63 unique commits, is NOT an ancestor of the current branch, and received commits one day before the current tip** (2026-10-01 vs 10-02), touching the same motion files the current branch evolved by 383 lines. Local `main` is itself 27 commits ahead of origin/main (unpushed). Decision needed before Phase 15: replay the demo experiments or abandon them. Also corrected: versionCode is already 4 / "0.4.0" on this branch (`app/build.gradle.kts:42-43`) — the handoff brief's 0.3.0 is stale.
