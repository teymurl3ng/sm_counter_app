# Phase 6 research: adapt established reminders to a small credit shop

16 October 2026. Source baseline `4fc8457`. Research and planning only. These are documented product behaviors, not a hands-on certification, market-share ranking or proof of how a vendor implements its backend. No app, database, phone or customer was changed/contacted.

The shared product pattern is eligibility + schedule + recipient controls + pause/history. It is not evidence that one specific frequency, collection escalation or messaging provider is an industry requirement. Sunday review, proposed defaults and the architecture below are our product judgments.

## Platform and delivery evidence

- [Android PeriodicWorkRequest](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest) documents battery/Doze delays and constraints. Use WorkManager plus foreground catch-up, with an approximate preferred time. No exact alarm, background screen opening or always-running service is justified for this feature. [Offline-first queue guidance](https://developer.android.com/topic/architecture/data-layer/offline-first) describes unique WorkManager work and durable queues; a unique name in one installation is not a cross-phone lock.
- [Android notification permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission) requires a denied-permission path. An in-app list must work independently of the Android notification. Notification posting is not proof of visibility or reading.
- [Google Play SMS policy](https://support.google.com/googleplay/android-developer/answer/10208820?hl=en) restricts sensitive SMS permissions and provides messaging intents as an alternative. This is a Play distribution constraint, not proof that Android technically forbids direct SMS in a privately installed APK. Eligibility of this shop app is unverified.
- [Android SmsManager](https://developer.android.com/reference/android/telephony/SmsManager) exposes SIM/subscription selection and distinct sending failures. A dedicated SIM phone is technically a candidate, but needs explicit subscription handling, handset availability and uncertain-result recovery. It does not solve cross-phone coordination or prove delivery.
- [Twilio Pakistan guidance](https://www.twilio.com/en-us/guidelines/pk/sms) documents route/sender limitations, possible sender substitution and no two-way support on that route. [Jazz messaging services](https://jazz.com.pk/business/solutions/messaging-solutions) establishes a local operator business-messaging offering. Neither establishes the correct account, API contract, approved sender, usable opt-out route or price for this shop. No quote, purchase, provider recommendation or legal determination is made here.
- [Supabase API security](https://supabase.com/docs/guides/api/securing-your-api) distinguishes grants, row access and function permissions. A shared coordinator needs shop/role authorization and atomic server operations, not client flags. The [changelog](https://supabase.com/changelog) identifies the Data API exposure-default change; future migrations must set privileges explicitly. The `.md` changelog fetch failed; the official indexed changelog and current MCP documentation were used instead. No live project query or mutation ran.

## What the existing implementation actually supports

Inspected the following, with hashes recorded in BASELINE.json:

- `CreditPaymentTerms.kt`: each sale retains 1–365 net days or one calendar month. One calendar month is sale-date plus a calendar month; it is not a universal month-end deadline.
- `CustomerCreditStatus.kt` and `CustomerCreditView.kt`: canonical current debt, agreed due-date evidence, partial/unknown coverage and Owner flags already exist. No new credit-aging or risk-score engine is needed.
- `CustomerCommunication.kt`, `ReminderIntents.kt` and the phase 5 UI: current-balance review, one-draft recipient override, manual composition and local/backup preparation history exist. They do not provide shared scheduling, shared acknowledgments or verified sending history.
- `CloudBackupScheduling.kt`, `SyncPushWorker.kt`, `SyncNotifier.kt`: WorkManager and permission-aware notifications have existing patterns to reuse. The reminder worker/channel must have its own names; do not reuse backup or sync identity/status.
- `BusinessClock.kt`: shop timezone and trusted-time fallback exist. Use the same clock; do not schedule using each phone's unrelated local timezone.
- `SyncIdentity.kt`: installation identity lives outside backup; restore can regenerate it. This helps identify a notification installation, but it is not independent server attestation of a person/device.
- `SyncRuntime.kt`, pull-state and credit-metadata migration: enrolled sync and a separately authorized metadata contract are available patterns. A pull cursor is not a guarantee that another offline phone has uploaded everything. No verified complete last-successful-exchange timestamp was found in this limited inspection; add an explicit freshness result at the existing successful exchange boundary if needed.
- Current Room schema is version 18. New shared/local scheduling metadata needs its own deliberate migration/restore/capability design. Phase 5's no-schema-change boundary does not apply to all of phase 6.

## Conclusion to carry into planning

Use one pending follow-up per customer, showing why it is present. Sunday statement preparation and overdue payment follow-up are separate reasons. Aggregate them for review; do not notify/send for every sale or call every positive balance late. Keep customer contact deliberate while owner detection, scheduling and shared review state become reliable. Record automatic SMS as a distinct route/activation decision, rather than quietly cancelling it or pretending that a composer is automatic delivery.

## Wi-Fi tablet follow-up

The owner's SIM question exposed a missing explicit manual-device fallback. [WhatsApp's tablet guidance](https://www.whatsapp.com/download/tablet) and [Android-tablet help](https://faq.whatsapp.com/670052398160812) document linked-device operation. The tablet's own SIM is not a prerequisite for a linked internet messaging app. [Android telephony capability](https://developer.android.com/reference/android/content/pm/PackageManager#FEATURE_TELEPHONY_MESSAGING) is distinct from the [SMS composer intent](https://developer.android.com/guide/components/intents-common#Messaging): a resolved composer does not establish an active subscription or transmission. A messaging app may relay through another phone; that remains external-app behavior to verify, not something this app has implemented. The provider option is SIM-independent on the operator device, whereas a dedicated-SIM route requires a separate suitable phone. No physical tablet or linked-app end-to-end test was performed during this documentation pass.
