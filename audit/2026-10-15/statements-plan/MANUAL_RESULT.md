# Phase 5 piece 3: manual reminders and observable local history

16 October 2026; baseline `6ffe8a8`. ✅ ~~Manual reminder review, WhatsApp/SMS handoff and local preparation history.~~ All three phase 5 pieces are implemented at their documented isolated QA scope. Signed ordinary-app delivery and human acceptance remain in phase 1; phase 6 automation/automatic-SMS decision remains unimplemented.

From Statements & reminders, Prepare reminder opens a dedicated scroll body under the existing Customers header/footer. Recipient and Message use the same native information surfaces, text hierarchy, colors, haptics and section insets. WhatsApp/SMS are vertical choices, with one Open action, reserved progress and persistent feedback. The customer and full normalized number remain visible for explicit recipient confirmation. Missing/ambiguous saved numbers require a full international number; an override applies only to this draft. An edited override uses the existing leave guard on Back/navigation, and Discard clears its saved draft state. The input is not automatically focused and the body owns its IME padding once.

Reminder facts are an authorized transactional read of shop/customer identity, saved phone, canonical current balance, business date and existing known-overdue facts. The selected statement's historical closing is never used. Neutral wording includes current outstanding and supported overdue amounts, explicitly labeling partial coverage. Settled and advance balances produce an explanation and disabled payment-request action. Private notes, Owner flags, credit limits and staff details are absent from the customer-facing facts/message. Customer/session context is checked before and after asynchronous work; balance, identity, phone, date or wording changes require renewed review/recipient confirmation before handoff. No financial, profile, payment-term or sync record is rewritten.

SMS uses ACTION_SENDTO/smsto and sms_body with no attachment or SEND_SMS permission. The preflight explains carrier charges. WhatsApp uses an encoded wa.me URL limited to the standard or Business app, with only those two package visibility declarations. Missing WhatsApp offers a deliberate SMS choice rather than silently opening a browser. Opening an app is not evidence of a sent/delivered message or of recipient registration. Files remain a separate Android share action.

Preparation history reuses the existing security-audit table under a dedicated action namespace. It stores customer UID, operation ID, statement period/reminder date, channel and observable action, with the existing actor/timestamp audit fields. It stores no message body, recipient override or amount. Exact action retries are idempotent; reads are customer-specific and limited to the latest 50. Existing backup serialization preserves these rows; live business sync does not distribute them. The screen explicitly describes local/possibly restored history. Labels distinguish Statement/Draft prepared, Share menu opened, Composer opened and Handoff failed. A history-save failure after an external launch preserves the launch outcome and adds a separate warning instead of falsely reporting handoff failure. External cancellation or delivery is unknown.

## Research and independent judgment

[Frozen execution scope](MANUAL_SCOPE.md) supplements the existing [functional plan](PLAN.md) and [UI brief](UI_FIT.md). Official [Android messaging intents](https://developer.android.com/guide/components/intents-common#Messaging) and [WhatsApp click-to-chat](https://faq.whatsapp.com/5913398998672934) were refreshed. Direct WhatsApp help body retrieval was unavailable; its official indexed text confirms international-number and encoded-text formatting. Existing native design material and Impeccable layout/typeset references were reused; no new design system or external messaging service was introduced.

The audit mechanism's actual entity, DAO, backup codec and existing consumers were inspected before reuse. A separate synced reminder table would add an unnecessary contract in this piece. A web fallback would not prove app-specific composition. Automatic sending/delivery claims would exceed both the observed Android behavior and the approved scope. The saved judgment hook emits a fixed reminder, not an implementation verdict.

## Affected acceptance

Twenty-one unique affected methods pass across [initial](manual-first-results.json), [corrected/capture](manual-final-results.json) and [final history](manual-history-final-results.json) runs: four reminder/intent/audit methods, six reminder UI methods, five directly touched statement/navigation methods and six sharing methods. Initial20/21 passed; the one failure expected exactly “Settled” while the actual message correctly included the no-reminder explanation. That assertion and three capture methods passed4/4 without changing the runtime APK. Final history date-label polish was followed by only its affected dark/200%-host navigation/history method. No full suite ran.

Checks cover current/overdue amounts, collection to settled/advance, read-only finance, private-data exclusion, explicit phone syntax and Unicode/special-character URI/message encoding, unauthorized sessions/Cashier/non-customer refusal, allowed action vocabulary, exact-action deduplication, customer separation/latest50 and existing backup-codec roundtrip. Native cases cover recipient confirmation, changed balance/phone after preparation, keep/discard override, a real numeric IME with input above it, missing-handler-to-SMS choice, busy controls, settled/advance/loading error, shared chrome bounds, navigation/return, and share-history persistence failure after a successful chooser launch.

Synthetic light/default and dark/200%-host screenshots were inspected for reminder top, long names/message wrapping and handoff feedback. The number input stays above the actual A06 keyboard without a large colored gap. Final preparation-history presentation uses labeled balance/period dates and a readable local recorded time; actions remain reachable through vertical scrolling. The existing 200% footer-label truncation is still the already recorded LATER.md item. Compose host-density tests do not certify every device-wide font setting, external composer or physical biometric/haptic feel.

All message launches were intercepted by synthetic test handlers; URI construction was checked independently. The existing real Android file chooser was opened/dismissed without selecting a recipient. Neither WhatsApp nor SMS was launched with a real customer. Only the disposable A06 QA target/test APK was installed/cleared, with package identity checked by the driver. No ordinary app, real-shop transaction, cloud, schema migration, actual sending or signed release was performed. Source/results/hashes and reproducible drivers are retained; raw logs and synthetic device screenshots stay local.

Local authoring corrections before device acceptance: fixed a generic-type/default-value parse error and moved haptic callback construction back into composable scope. Wiring/driver commands that initially used repository-relative paths from phase18 were rerun from the repository root. These are build/tool errors, not production defects or successful acceptance runs.
