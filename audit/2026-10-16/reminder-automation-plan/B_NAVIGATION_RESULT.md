## Research and judgment

Used current [Compose state-saving guidance](https://developer.android.com/develop/ui/compose/state-saving), existing Android messaging/lifecycle references and inspected native components. Saved state holds identifiers and presentation choices, not financial authority. Re-read current facts on use. Reviewed [Supabase functions](https://supabase.com/docs/guides/database/functions), the current changelog and the [TLS notice](https://supabase.com/changelog/cbc-tls-ciphers-deprecated); no protocol, key, SDK or TLS configuration changes are needed here. The test-only fix follows the [official Espresso3.7.0 release](https://developer.android.com/jetpack/androidx/releases/test#espresso-3.7.0); resolved3.5.0 and the successful rerun establish its relevance to this device rather than assuming all test failures are app defects.

The finish hook is a reminder, not approval. Selecting nullable shared access once per screen would make stale mode a bypass; live mode revalidation is necessary. Requiring a connection on synced installations is a deliberate availability tradeoff. A database read and an external activity cannot form one atomic transaction: no exactly-once sending, knowledge of unuploaded payments or immunity to contact outside this workflow is claimed. Existing server coordination still needs real concurrent two-phone acceptance. The ordinary route wiring in source does not mean reminders have been activated on a shop or notifications scheduled.
